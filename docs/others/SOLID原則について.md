# SOLID原則について

ソフトウェア工学の用語であり、ソフトウェアの拡張性や保守性を高めるための開発原則のこと。

以下の5つで構成される。

- SRP: 単一責任の原則
- OCP: オープン/クローズドの原則
- LSP: リスコフの置換原則
- ISP: インターフェース分離の原則
- DIP: 依存性逆転の原則

**Solid原則を守るメリット**

- 拡張性の向上: 変更しやすい、再利用しやすい
- 保守性の向上: 変更に強い
- 可読性の向上: 理解しやすい

## SRP: 単一責任の原則

Single responsibility principle（単一責任の原則）とは、「すべてのモジュールにおいて、それが持つ責務は1つとする」という原則である。
クラスやモジュール、関数が変更する理由は1つだけであるべきで、実行することも1つである必要があるという考え方のこと。

### Point

この原則は、**モジュールは1つのことを行うべきという原則ではない。**
あくまで、「責務を負う対象を1つにする」という原則である。
「関数はたった1つのことを行うべき」という法則も存在するが、単一責任の原則はそれとは異なるものである。

また、**同じロジックは1つにまとめて共通化しようという話でもない。**
むしろ、アクターの異なるモジュールは分割し、それぞれのアクターに対して異なるモジュールを作成すべきである。
そもそもの概念が異なるものは、まとめてはならない。

### この原則を守らないとどうなるか

- 依存関係が複雑になり、1つの役割の変更が、別の役割にも影響を与えるようになってしまうため、バグを生みやすくなる
- 何かを変更するたびに、その変更の影響を受ける箇所を調査し、変更後にテストしないといけなくなるため、無駄に多い工数がかかってしまう
- 保守性が低下する

### この原則を守るメリット

- 変更箇所を最小にできる: 変更による影響を最小限にでき、変更の影響が他の部分に及ばないため、変更箇所をテストするのに時間がかからない
- 変更箇所が明確になる: どこを変更すればよいのかすぐにわかるため、変更箇所を探すのに時間がかからなくなる
- 可読と拡張性が向上する: 他のモジュールから利用しやすくなる

### 守るために心掛けること

#### モジュールを機能ごとに小さく作る

モジュールを機能ごとに小さく作るようにする。
ネジや板のように、それ以上分割したら機能しなくなるレベルまで分割していく。

それ以上分割したら機能しなくなるレベルまで分割したモジュールを組み合わせて大きなシステムを構築していく。

#### 概念が異なるものは分ける

たとえ同じようなロジックであっても、概念が異なる場合は別のモジュールに分割する。
コードの繰り返しは避けるべきだが、そもそもの概念が異なるものをまとめてはならない。

処理が似通っていても、アウトプットが異なるなら、アクターごとにクラスや関数を分割する。

## OCP: オープン/クローズドの原則

Open/closed principle（オープン・クローズドの原則）とは、「モジュールは、拡張に対しては開いていて、変更に対しては閉じていなければならない」という原則である。

### Point

- 拡張: 機能追加のことを指し、拡張に対して開かれているとは、新しいコードを追加すれば機能を追加できるということである。
- 変更: 既存のコードの修正のことを指し、変更に対して閉じているとは、機能追加によって既存のコードが修正されないということである。

オープン・クローズドの原則を言いかえると、「モジュールは、既存のコードを変更せず新しい機能を追加できるようにすべきである」となる。

### この原則を守らないとどうなるか

- 機能を追加する際、既存のコードに手を加えなければならないため、それまで問題なく動いていた既存のコードへ影響を与えてしまう危険性がある。
- 既存のコードへ影響を与えてしまう危険性があるため、保守性が低下し、バグが発生しやすくなる。（変更が軽微なものであっても、ケアレスミス▽が発生する可能性が高くなる。)
- 既存のコードに手を加えてしまうため、既存のコードを修正するたびテストが必要になり、テストにかかる工数が増大してしまう。

### この原則を守るメリット

- 拡張が容易になる。
- 拡張時に既存のコードへ影響を与えないため、拡張機能だけをテストすればよくなるため、保守性が向上する。
